# Fixed Timestep & Accumulator — Implementation Guide

*This is the concrete "how" behind Part 4, Exercise 2, and `02_ROADMAP.md`'s "not started yet." Your separate experiment file explains exactly why: this pattern was being prototyped in isolation before going anywhere near `main.c` — which is exactly the right way to de-risk it. Below is what that experiment gets right, the one real bug in it, and how it plugs into the actual game.*

## What the experiment already gets right

Worth naming clearly, since the rest of this is mostly correction-notes:

- **`frameTime` is clamped to 0.25s before it hits the accumulator.** This is the standard "spiral of death" guard Part 4's own doc warns about — without it, a single lag spike could force the catch-up loop to try to simulate seconds of missed time in one burst, which itself takes real time, causing more lag, compounding forever.
- **`alpha` is already being computed** (`accumulator / dt`) — this is exactly the value a fixed-timestep engine uses to interpolate rendering between the last two simulation states, so motion looks smooth even when the render rate and the fixed update rate don't line up exactly. It isn't *used* for anything yet (there's no previous-position snapshot to interpolate from), but having it computed and printed already is the right first step. More on this below.
- **FPS/UPS instrumentation** — printing renders-per-second alongside updates-per-second once a second is a genuinely good habit; it's the cheapest way to visually confirm the update rate is holding steady at 60 regardless of what the render loop is doing.

## The one real bug: the update cap doesn't actually cap

```c
int updateCount = 0;
const int maxUpdates = 5;

while (accumulator >= dt && updateCount <= maxUpdates){
  // ----------------UPDATE HERE----------------
  ...
  accumulator -= dt;
  updateCount++;
  updateCountTotal++;
}

// If we do max updates per cycle or accumulated time, then we reset so we dont do too many updates
if (updateCount == maxUpdates){
  accumulator = 0;
}
```

Trace it by hand: the loop checks `updateCount <= maxUpdates` *before* incrementing, so it still runs when `updateCount` is `5` (`5 <= 5` is true) — meaning it actually runs **6** times whenever there's enough backlog, and `updateCount` ends at `6`, not `5`. The follow-up check, `if (updateCount == maxUpdates)`, compares against `5` — which is now never true in exactly the one scenario it exists to catch. The safety valve that's supposed to say "we hit the cap, throw away whatever's left instead of carrying it forward" silently never fires.

The practical effect: after a big lag spike, the leftover backlog doesn't get discarded — it carries into the next frame's `accumulator`, and the next, until enough spare frames pay it down. Not an infinite spiral on its own, but it defeats the exact backstop the comment says it's there for, and if the machine stays overloaded for a stretch (real elapsed time per frame regularly exceeding what 6 updates can pay down), the backlog can grow without the bound this code intends to give it.

**Fix:** change the loop condition to a strict `<`:

```c
while (accumulator >= dt && updateCount < maxUpdates){
```

With that one change, the loop stops at exactly `updateCount == 5`, and the `if (updateCount == maxUpdates)` check correctly fires when the cap is actually hit.

## Smaller things worth tidying up before this moves into the real game

- **`now()` is a fairly collision-prone name for a function.** It works here because it's the only file, but once this rejoins `terminal_utils.c`/`.h`, a name that generic is easy to accidentally shadow or clash with. Keeping the original `timeNow()` (or similar) is probably safer.
- **The helper functions have all lost their `static`.** `enableRawMode`, `disableRawMode`, `handleSigint`, `mapCharToKey`, `setKeyDown`, and `handleEscapedSequences` were all `static` in `terminal_utils.c` (internal linkage — not visible outside that file). Harmless in a single-file experiment, but worth restoring `static` on all of them once this is split back into `.c`/`.h` files, so they don't leak as globally visible symbols.
- **`handleSigint` dropped its `(int sig)` parameter.** `signal()` expects a handler shaped like `void (*)(int)`; the original file matched that exactly (`void handleSigint(int sig) { (void)sig; ... }`). The zero-parameter version here works in practice on Linux/GCC, but isn't a strict signature match — worth keeping the `(int sig)` parameter when this goes back in.
- **`sleep_seconds` doesn't retry on interruption.** The original `sleepMs` looped on `nanosleep` specifically to handle being woken early by a signal (`while (nanosleep(&ts, &ts) == -1) continue;`). `sleep_seconds` here calls it once. Probably fine, but worth carrying the retry loop over if you want the same robustness.
- **`dt = 1.0 / 60.0` is `0.016667`, not `0.016`.** Close to the old `secondsPerFrame`, but not identical — worth using the exact fraction now that timing is being measured precisely rather than assumed.

## Plugging this into the actual game

The core shape carries over almost directly. Roughly:

```c
double currentTime = timeNow();
double accumulator = 0.0;
const double dt = game->secondsPerFrame; // reused as the fixed step, not "assumed frame length"

while (game->isRunning) {
  double frameStart = timeNow();
  double frameTime = frameStart - currentTime;
  currentTime = frameStart;
  if (frameTime > 0.25) frameTime = 0.25;

  beginInputFrame(keyPair.keys);
  updateInput(keyPair.keys, keyPair.lastSeen);
  // read held keys into player->vx/vy here, same as gamePlaying() does today

  accumulator += frameTime;
  int updateCount = 0;
  const int maxUpdates = 5;
  while (accumulator >= dt && updateCount < maxUpdates) {
    updateUnitsPositions(game);
    checkBuletPositions(game);
    clampObjectsToBorders(game);
    accumulator -= dt;
    updateCount++;
  }
  if (updateCount == maxUpdates) accumulator = 0;

  printf("\033[H\033[J");
  renderMap(game);   // rendering stays outside the inner loop — once per outer iteration

  double elapsed = timeNow() - frameStart;
  if (elapsed < dt) sleepMs((dt - elapsed) * 1000);
}
```

A few things worth deciding as you do this, rather than following the sketch above blindly:

- **`bulletLimiter` belongs inside the inner loop, not outside it.** It's a simulated-time quantity (a cooldown measured in `dt` units), so it should advance once per fixed update, alongside `updateUnitsPositions` — not once per outer/render iteration. If it stays outside, it'll drift relative to the actual simulated time whenever more than one inner update runs in a single outer pass.
- **Where the state machine fits is your call.** The sketch above assumes the accumulator loop always runs the `PLAYING`-state simulation, but `gameMenu`/`gamePaused`/`gameWin`/`gameLose` don't want any of this running. Either keep the whole accumulator structure inside `gamePlaying()` and simply not invoke it for other states, or hoist it to the outer loop and gate the inner update call on `game->gameState == PLAYING`. Both are reasonable; the first is less disruptive to what you already have.
- **Switch `secondsPerFrame` (and `accumulator`/`currentTime`) to `double`.** `float` has enough precision for a single frame's math, but accumulating many small additions over a long play session benefits from `double`'s extra precision — which the experiment already does correctly.

## About `alpha`, for later

`alpha` is the fraction of a not-yet-simulated timestep sitting in the accumulator — the standard input to interpolated rendering (`renderedPos = lerp(previousPos, currentPos, alpha)`), which is what keeps motion looking smooth when the render rate and the fixed update rate don't match up exactly. It's not needed to call this exercise "done" — using it means keeping a previous-frame position snapshot per unit, which doesn't exist yet. Worth revisiting once rendering feels choppy and not before; for a terminal renderer capped at ~60 outer iterations a second anyway, you may not even need it until the SDL port.
